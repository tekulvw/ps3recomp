## How to update

- Change an item's **Status** in the table below whenever its state changes, in the same fork PR that
  does the work, or in a small docs PR. Use exactly one of: `not started`, `in progress`,
  `PR open #N`, `merged #N`, `dropped (reason)`. Upstream PR numbers are on `sp00nznet/ps3recomp`.
- When an upstream PR merges, note the upstream merge commit next to it. When upstream lands its own
  equivalent, mark ours `dropped (superseded by upstream #N)` and move a line to section 5.
- Add new candidates at the end of the matching section with the next free ID (Q14, M15, ...), and
  add a row to the table.
- Re-check upstream before sending anything: fetch `master`, search open and merged PRs for the same
  area, and re-measure where an item claims a speed-up.
- Each upstream PR is its own branch from current upstream `master` (`upstream/<topic>`), carries a
  synthetic test, has fork-only dependencies and title-specific wording removed, and uses a neutral
  conventional-commit message. Never include game files, extracted data, game addresses, private
  paths or session links, here or upstream.

**Q2. glibc static TLS: thread stacks that are too small**
- **Commits:** fork 8840a9dd (+62) and 57a249d3 (+7, a `syscall` prototype under strict POSIX). mag-recomp 9252afc (#46) is the same insight applied to Rust threads.
- **Files:** `runtime/platform/win32_compat.{c,h}`, `runtime/platform/tests/test_win32_compat.c`.
- **Value:** glibc takes static TLS out of the requested stack. With a large TLS, every 1 MB `CreateThread` fails with EINVAL, and SPURS init then returns NOMEM. That only bites when the TLS is large (our 2 MiB decode cache), so check upstream's TLS size first. The fix is harmless either way.
- **Seen for real (2026-11-08):** on Linux, SPURS's 1 MiB worker threads failed to start once a
  2 MiB thread-local SPU decode cache was in the binary. mag-recomp #134 worked around it by moving
  that cache to the heap; the stack-sizing fix is still the general cure.
- **Risk:** low; Linux/glibc only.
- **Prerequisites:** remove the include of fork-only `diagnostics/original_work_threads.h`.
- **Upstream PR title:** "fix(platform): add glibc's static-TLS overhead to CreateThread stack sizes"

**Q5. SPU task thread pool**
- **Commits:** c1c07bfe (+98, POSIX), then the shared `runtime/spu/spu_task_pool.inc` with a Windows pool and per-task thread hygiene.
- **Value:** `PS3RECOMP_SPU_TASK_POOL=1` reuses host threads for async SPU tasks on Windows and POSIX. A thread is reused only when one is idle, so a task is never queued behind another and there is no deadlock risk. We measured about 2,200 thread births in 6 s on Mac without it. Every task, pooled or not, now drops lock-line and MFC registrations left on its stack (POSIX never did), and a reused thread resets the per-task cri EXIT count.
- **Risk:** low; off by default.
- **Tests:** `tools/test_spu_task_pool.py` (Windows and POSIX), `tools/test_spu_async_task_pool.py` (POSIX, real dispatch).
- **Upstream PR title:** "perf(spu): opt-in host thread pool for async SPU tasks"

**Q18. Event queues published only once initialised**
- **Source:** fork #67 (`runtime/syscalls/sys_event.c`, `runtime/syscalls/tests/test_sys_event_queue_race.c`, `tools/test_sys_event_queue_race.py`; +176/−18).
- **The bug, present upstream:** both create paths (`sys_event_queue_create` and `sys_event_queue_create_direct`) set `active = 1` before they initialise the queue's lock and condition variable. `sys_event_find_queue_by_key` and `sys_event_queue_push_by_id` read `active` without a lock, so a host producer (the cellAudio period thread, SPURS, SPU groups) can enter a zeroed lock. Destroy has the mirror race. The Windows table lock is initialised through an unsynchronised flag.
- **Fix:** initialise first and publish `active` last with a release store; clear it first on destroy; look up and push under the table lock; initialise the Windows table lock with `InitOnceExecuteOnce`.
- **Value:** high. It crashed the downstream title on about 1 in 6 Windows engine starts (a write near address 0x24 inside `EnterCriticalSection`). POSIX only works by accident on glibc.
- **Risk:** low. The synthetic test faults on the old file on its first run on Windows and passes with the fix.
- **Prerequisites:** none. The patch needs a small rebase: one hunk of `sys_event.c` does not apply to upstream as is.
- **Upstream PR title:** "fix(lv2): publish event queues only once initialised; push under the table lock"

**Q19. Per-task scrub of stack-keyed SPU registrations**
- **Source:** fork #47 (`runtime/spu/spu_task_pool.inc`, `spu_workload.c`, `tools/test_spu_task_pool.py`, `tools/test_spu_async_task_pool.py`).
- **The bug, present upstream:** lock-line reservers and MFC engines are keyed by the `spu_context` pointer, and job contexts live on the task thread's stack. Upstream drops a context that leaked past its unregister only when a Windows async-task thread exits; on POSIX it never does. Store to module start: about 1 ms (the coordinator's timed pass) to 17 µs. It writes no guest state, so the fork has it on; `PS3RECOMP_SPURS_STORE_WAKE=0` turns it off.
- **Value:** high for SPURS titles. In game, together with Q22's fork #77, it added +2.9% on Windows; the synthetic hop latencies above are the clearer signal.
- **Risk:** medium (scheduler wake-ups). Admission is unchanged; the coordinator's selection moves verbatim into `spurs_dispatch_slot()`.
- **Prerequisites:** rebase onto upstream `cellSpurs.c`; fork #81 uses `spu_coh_watch_add`, which upstream has.
- **Upstream PR titles:** "perf(spurs): wake only the worker a dispatch fills", "perf(spurs): wake the coordinator when a write lands on the request line"

**M20. SPU micro-interpreter decoded-run cache**
- **Source:** fork #85 (`runtime/spu/spu_channels.c` +179, `test_spu_smc_trace.c`, `tools/test_spu_smc_trace.py`).
- **Contents:** `spu_smc_microstep` keeps a small per-thread cache of decoded straight runs (entry to the first unconditional branch) and replays one only while its words still equal the decoded bytes. A store into the run stops the replay. Instruction-level observers keep the ordinary path; `PS3RECOMP_SPU_SMC_TRACE=0` turns it off.
- **Value:** medium. It pays off for code that a job manager regenerates at runtime and so can never be lifted. A 121-instruction stub went from 226 to 145 ns per call; Linux +4.4% in game, Windows within noise.
- **Risk:** low to medium; a randomized differential test compares registers, the whole local store and the pc with the cache on and off, and two mutants fail it.
- **Prerequisites:** none known; upstream's `spu_smc_microstep` has the same shape.
- **Upstream PR title:** "perf(spu): replay the micro-interpreter's decoded runs while their words are unchanged"

**M21. Delta-driven draw engine**
- **Sources, in order:**
  1. fork #51: the dispatcher records which vertex constants were written since the last draw, the engine copies only those, and a new optional backend hook `rebind_vs_constants` reuses an unchanged upload (Metal and Vulkan implement it). About 5 ms per frame of memmove/memset on the Linux FIFO thread.
  2. fork #53: each texture unit is decoded once per draw, and fragment-program products (sampled units, WPOS, constants, gamma and expansion units, the structural hash) are kept for the last 8 programs, byte-validated so a constant patched into the program in place is seen. About 3.6 ms per frame on Linux.
  3. fork #55: a Metal render encoder is sent only the state a draw changes; a random-stream test sent 18,574 binding calls instead of 158,644.
- **Value:** high for CPU-bound RSX threads on every backend. The fork's Linux A/B of fork #49–#57 together, with Vulkan pass merging on, was +11.9%.
- **Risk:** low; no switch, and the bytes each draw sees are identical.
- **Prerequisites:** upstream's draw engine, Metal and Vulkan files have diverged from the fork by thousands of lines; re-implement on upstream. The Vulkan half of fork #51 targets the fork's batched recorder (see M22). Fork #79 and #86 (staging only the constant rows a program reads) build on this but measured no gain; they stay in the fork.
- **Upstream PR titles:** "perf(video): copy only written vertex constants per draw, and reuse unchanged uploads", "perf(video): decode a draw's texture units once and keep fragment-program products", "perf(video): send a Metal render encoder only the state a draw changes"

**M22. Vulkan engine driver-cost series**
- **Sources:** fork #39 (object churn and present waits), #50 (`PS3RECOMP_VK_MERGE_PASSES`: same-target draws share one render pass), #57 (`PS3RECOMP_VK_DESCRIPTOR_REUSE`: dynamic constant offsets, so sets can be shared) and #60 (batch arenas grow when full).
- **Value:** high for Vulkan. With the report batch raised, pass merging took the Linux RSX thread from 97% to 64% busy and the GPU from 74% to 24%; fork #39 cut fence waits from about 355 to 19 a second and framebuffer churn from 262 to 48.
- **Blocker:** fork #50, #57 and #60 apply only to the fork's batched recorder (`PS3RECOMP_VK_BATCHED_ENGINE`), which section 5 says not to send because upstream has its own (#532, `VK_DRAW_BATCH`). They need re-implementing on #532's recorder, or a discussion about which recorder upstream wants. Parts of fork #39 overlap upstream #552 (staging reuse) and M4's present ring.
- **Upstream PR titles:** "perf(video): merge same-target Vulkan engine draws into one render pass", "perf(video): reuse Vulkan descriptor sets with dynamic constant offsets", "perf(video): cut Vulkan engine object churn"

**M23. Opt-in plain-method FIFO walk**
- **Sources:** fork #54 (`PS3RECOMP_GCM_FAST_WALK=1`, `tools/test_gcm_plain_walk.py`) and fork #70 (comments that tie the exception list to the general path).
- **Contents:** a data word of a plain 3D packet goes straight to the draw engine, skipping the per-word diagnostic checks, the per-word IO-table lookup and the report checks, unless its method is one of the few with effects of their own. The IO table is consulted once per 1 MB page. A test walks one synthetic FIFO both ways and requires identical engine calls.
- **Value:** high where the FIFO thread limits the frame rate: +12.7% on Metal in game.
- **Risk:** medium. A new per-method effect on the general path must be added to the exception list.
- **Prerequisites:** upstream's walker differs from the fork's (about 2k lines of `cellGcmSys.c` divergence), and the lock-free picture-readiness half is for a fork-only registry. Re-seat on upstream's walker.
- **Upstream PR title:** "perf(gcm): opt-in plain-method path through the FIFO walker"

## 3. Large / architectural (discussion first)

**A1. Checked GPU completion for RSX reports and labels, with opt-in early release**
- **Fork work:**
  - c673e27f, fc79163a, cbc3cb99: deferred reports with GPU tickets;
  - d1aefd9d, a10addbd, 4028d97f and `docs/RSX_EARLY_LABEL_RELEASE.md`: early release;
  - 6c2feee7: inline-image barrier without a GPU wait (menu went from about 9 to 57 flips/s);
  - ed3034f1: batch knob;
  - 9ba1ed20 / 0a2d3d17: the live D3D12 equivalent.
- **Size:** several thousand lines in `cellGcmSys.c`.
- **Pitch:**
  - Upstream publishes labels and reports at FIFO position, and has no record of whether the GPU work ahead of them finished.
  - The fork queues each report behind a backend completion ticket, applies it in order, and freezes on failure. That makes "label written" mean "work done". Async backends can then batch and pipeline without guests reading early results.
  - The early-release mode gives most of the latency back for engines that snapshot their GPU inputs at record time.
  - Upstream should first decide whether it wants these semantics. The `cellGcmSys.c` diff is too large to review cold.
- **Upstream issue title:** "RFC: ordered, completion-checked RSX report and label publication for async backends"

**A2. A native-owner seam: let a host renderer replace RSX work**
- **Fork work:** `rsx_native_owner.h`, `rsx_native_owner_gate.h`, `rsx_native_handoff.h`, `rsx_native_{image,frame}.h`, `rsx_frontend*.c` and `docs/FRONTEND_COMPUTE.md` (fork PR #14, codex/render-frontend-api); Vulkan reserved queue order c7823158; Metal queue order on `feat/metal-queue-order`; D3D12 owner and target leases on `claude/d3d12-native-owner` and `-native-targets`.
- **Related:** mag-recomp `mag_render_host_bridge` (the consumer side); mag_decomp's RSX state-preamble encoder and completion-receipt ideas (clean-room rewrite only).
- **Pitch:**
  - Ports that want to render some passes natively need four things from the SDK: borrow its device and queue with lifetime and generation checks; lease its colour and depth targets; reserve a spot in its queue order; and take over a published command span at an exact FIFO position.
  - We have a versioned C ABI for all four on Metal, Vulkan and D3D12, off by default.
  - The current handoff API is shaped around one title's ring writer. A discussion would settle a smaller generic core first: owner borrow, image lease and queue reservation.
- **Upstream issue title:** "RFC: borrowed native-owner and image-lease ABI for external render frontends"

**A3. A decoupled RSX consumer: one framing for M5, M6, A1 and A2**
- **Pitch:**
  - Present on its own thread, account for FIFO-thread time, publish labels at the earliest correct point, and let an extension own spans.
  - Together these turn the walker into a thread that never blocks on the display or the GPU.
  - Worth one design note upstream, so the PRs land in a coherent order and don't trickle in one at a time.
- **New fork material (2026-11-09):** fork #58 (design notes for a second RSX encode thread and host-format vertex streams); fork #73 (opt-in `PS3RECOMP_RSX_ENCODE_THREAD`: the Metal record replay moves to its own thread, ordered by enqueueing each command buffer on the walker; +9.8% in game on Metal); a Vulkan encode thread on the same design is in progress. Both depend on the fork's completion tickets (A1) and staging arenas, so they belong in this design note, not a cold PR.

**A4. Coherence model next steps**
- **Covers:** M2 plus the deferred redesign (per-line version counters and lazy delivery of lost reservations).
- **Pitch:**
  - Upstream's lock-line, context-walk and notify model costs about 2.7 ms per update on our Mac game thread even after the fast paths.
  - A per-line version-counter model would remove the global walks.
  - Propose this only once you lift the "after the reset" hold, with a clean-room spec.
- **Now implemented (fork #78, opt-in `PS3RECOMP_COH_VERSIONS=1`, about 2.7k lines):** one 32-bit word per 128-byte line (a writing bit, a waiters bit and a count every completed write advances). A reservation records the count; PUTLLC and stwcx./stdcx. commit only while it is unchanged; GETLLAR is a seqlock read; a lost reservation is delivered lazily wherever the SPU can observe it, and a writer wakes only parked holders. About 65 host read-modify-write sections go through `spu_coh_write_begin/end`. Measured +12.6% on Linux (with a 15-minute soak), +10.2% on Mac and +8.3% on Windows. Fork #87 makes the coherence fixtures check the guest-visible contract under both schemes.
- **For upstream:** a discussion with the design and these numbers first. It touches every lock-line call site and the SPURS, Sync and GCM HLE.

**A5. Lifter performance passes**
- **Pitch:** keeping guest registers in C locals (SPU `--promote-registers`, 4a59f6f0) was measured as neutral and reverted (b79c5252). That is useful negative data for upstream. Raw stack and private access, dead CR/XER elimination and direct calls are still proposals and are not approved even internally. Start with measurement, not a PR.
- **Update 2026-11-09:** the new SPU `--promote-regs` (fork #46) is a different, function-wide design and measured +6.8% on Windows. It is now M18.

**A6. Porting workflow: installer framework and clean-room method**
- **Sources:**
  - mag-recomp `installer/mag_installer/{tools,pipeline,safety,model,platforms,capacity}.py`: about 950 generic lines with pinned downloads, bounded extraction and transactional staging;
  - `docs/native-graphics-reimplementation-method.md`;
  - the job I/O recorder (`runtime/diagnostics/job_io_recorder.c`, fork-only) with `tools/jobio.py`;
  - mag_decomp's single-function replay harness design.
- **Pitch:** a reusable source-kit installer, plus a documented spec-then-implement method with a black-box SPU job recorder. Today every port reinvents these.
